# Мини-CRM «Объекты и задачи» (Строительная компания)

Полнофункциональная мини-CRM для строительной компании с разграничением прав доступа, конечным автоматом статусов задач на уровне СУБД (PostgreSQL / Supabase) и неизменяемой историей аудита.

Стек: **React 18 + TypeScript + Vite + Tailwind CSS + Supabase (PostgreSQL 17)**.

---

## 🚀 Быстрый запуск

### 1. Установка зависимостей
```bash
npm install
```

### 2. Настройка переменных окружения
Создайте файл `.env` на основе `.env.example`:
```bash
cp .env.example .env
```
Заполните ваши ключи Supabase:
```env
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=your-supabase-anon-key
SUPABASE_DB_HOST=aws-0-eu-west-1.pooler.supabase.com
SUPABASE_DB_PORT=5432
SUPABASE_DB_USER=postgres.your-project-ref
SUPABASE_DB_PASSWORD=your-db-password
```

### 3. Запуск локального сервера разработки
```bash
npm run dev
```
Приложение откроется по адресу `http://localhost:3000`.

### 4. Сборка для продакшена
```bash
npm run build
npm run preview
```

## 🛡️ Безопасность и архитектура (Требования раздела 3)

1. **Row Level Security (RLS) на уровне PostgreSQL**:
   - `objects`: исполнитель видит **только те объекты**, где у него есть хотя бы одна назначенная задача (`EXISTS (SELECT 1 FROM tasks WHERE tasks.object_id = objects.id AND tasks.executor_id = auth.uid())`). Объекты без его задач физически не возвращаются базой данных.
   - `tasks`: исполнитель видит и может изменять **только свои задачи** (`executor_id = auth.uid()`). Чужие задачи недоступны даже при прямом запросе по ID.
   - `task_history`: исполнитель видит историю только своих задач.

2. **Защита переходов статусов в базе данных (State Machine Trigger)**:
   - В PostgreSQL настроен триггер `BEFORE UPDATE ON public.tasks`, который проверяет допустимость перехода:
     - `Новая` → `В работе` (только назначенный исполнитель)
     - `В работе` → `На проверке` (только назначенный исполнитель)
     - `На проверке` → `Принята` (только постановщик)
     - `На проверке` → `На доработке` (только постановщик, **комментарий обязателен**)
     - `На доработке` → `В работе` (только назначенный исполнитель)
   - При любой попытке перепрыгнуть статус (например, сразу из «Новая» в «Принята») или изменить статус не той ролью транзакция отклоняется базой данных с `RAISE EXCEPTION`.

3. **Защита от изменения параметров задачи исполнителем**:
   - Исполнитель не может переименовать задачу, сменить объект или переназначить исполнителя — триггер на уровне БД блокирует любые изменения полей, кроме статуса.

4. **Неизменяемая история статусов (Audit Log)**:
   - Таблица `public.task_history` **не имеет политик INSERT, UPDATE или DELETE** для клиентских ролей (`authenticated`, `anon`).
   - Запись в историю формируется автоматически серверным триггером `SECURITY DEFINER` в той же транзакции.
   - Клиент через API физически не может подделать, изменить или удалить запись истории.

5. **Отключение открытой регистрации**:
   - Регистрация сторонних пользователей закрыта, пользователи управляются централизованно.

6. **Секретные ключи изолированы**:
   - Файл `.env` исключен из репозитория через `.gitignore`. На клиенте используется только публичный анонимный ключ.

## 🧪 Автоматическая проверка безопасности

В проект включен скрипт верификации всех 5 ключевых требований безопасности:
```bash
npm run db:verify
```
Он проверяет:
- Корректность изоляции объектов и задач для исполнителя;
- Блокировку попыток прочитать или обновить чужие задачи через RLS;
- Блокировку запрещенных переходов статусов на стороне СУБД;
- Блокировку прямой вставки/изменения истории через API.

Для повторного сброса и засеивания базы начальными данными:
```bash
npm run db:setup
```

   - `TaskCard` и `StatusBadge` обернуты в `React.memo`.
